# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Operis is a multi-tenant business management SaaS (sales, purchases, inventory, accounts receivable/payable, reports). The domain language, UI copy, and much of the docs are in Brazilian Portuguese. `AGENTS.md` holds the Laravel Boost guidelines (versions, Boost MCP tools, Pint/Pest/Inertia rules) and a running dev log; follow it. Project skills live in `.agents/skills/` (pest-testing, inertia-react-development, wayfinder-development, tailwindcss-development, laravel-best-practices, speckit-*). Domain specs are in `docs/` and `specs/`.

## Commands

```bash
composer run dev                 # artisan serve + queue:listen + vite, all at once
pnpm dev / pnpm build            # Vite only

DB_DATABASE=operis_test_main php artisan test --compact                            # all tests
DB_DATABASE=operis_test_main php artisan test --compact tests/Feature/Sales        # one directory/file
DB_DATABASE=operis_test_main php artisan test --compact --filter="creates a sale"  # one test

vendor/bin/pint --dirty --format agent   # format changed PHP (required after PHP edits)
pnpm lint            # eslint --fix
pnpm format          # prettier on resources/
pnpm types:check     # tsc --noEmit
composer run ci:check  # eslint + prettier + tsc + pint --test + tests
php artisan wayfinder:generate   # regenerate TS route/action helpers
```

**Production dumps:** the production MySQL session runs at −03:00 while Laravel writes UTC, and `TIMESTAMP` columns are converted by that offset; phpMyAdmin exports them in UTC (`SET time_zone = "+00:00"`). Import a production dump with that line changed to `SET time_zone = "+03:00"` (e.g. `sed 's/^SET time_zone = "+00:00";$/SET time_zone = "+03:00";/'`), or every created_at/received_at comes 3 h ahead. Never change the production connection timezone: its data is consistent as it is. Dumps live in `docs/dumps/` (gitignored).

Tests run against **MySQL** (`phpunit.xml` sets `DB_CONNECTION=mysql`, not sqlite), so a MySQL database must be reachable. Feature tests use `RefreshDatabase` automatically (`tests/Pest.php`), which wipes whatever database is configured: always pass `DB_DATABASE=operis_test_main` (a test-only database in the Docker MySQL) so the dev data survives. Page tests read the Vite manifest; if they fail with "Unable to locate file in Vite manifest" and the dev server is not running, run `npx vite build` first.

`vite.config.ts` ignores `**/.claude/**`: agent worktrees live there with their own `vendor`/`node_modules` and used to exhaust the file watcher (`ENOSPC`), killing `composer run dev`.

## Architecture

### Two separate HTTP surfaces
- **`routes/web.php`** only renders Inertia shells (`Route::inertia('dashboard/sales', 'dashboard/sales')`) — no page props carry data. Pages live in `resources/js/pages/` and every screen is a module there (see Front-end module structure); there is no `features/` folder any more.
- **`routes/api.php`** is a JSON REST API (Sanctum stateful/cookie auth via `statefulApi()`). All data is fetched client-side from it. Business routes sit behind the middleware chain `auth:sanctum → company.current → company.user → company.member → company.verified` (aliases defined in `bootstrap/app.php`).

### Multi-tenancy
Tenant = `Company`. The active tenant is `users.current_company_id` (resolved by `SetCurrentCompany` / `CurrentCompanyResolver`). Tenant-owned models use the `BelongsToCompany` trait (`scopeForCompany`), and controllers pass `auth()->user()->current_company_id` explicitly into services. Always scope queries by company; authorize model-bound actions via Policies (`$this->authorize('view', $sale)`).

### Backend layering
`Controller (Api/<Domain>/) → FormRequest (Requests/<Domain>/) → Service (Services/<Domain>/) → Repository (Repositories/Contracts + Eloquent, bound in AppServiceProvider) → Model`, responses via `Http/Resources/<Domain>/` wrapped as `{ data: ... }`. Single-action endpoints (cancel, payment/settlement, import) are invokable controllers. Status values are PHP enums in `app/Enums` (`SaleStatus`, `PurchaseStatus`, `FinancialStatus`, `PaymentMethod`, `StockMovementType`, ...).

### Cross-domain side effects (the core business logic)
`SaleService` and the purchase service orchestrate, inside `DB::transaction`:
- **Stock**: every create/update/cancel/delete writes `StockMovement`s through `StockMovementService` (update applies a diff between old and new items; cancel/delete reverse). `allow_negative_stock` bypasses the availability check.
- **Finance**: sales generate `AccountReceivable` installments via `ReceivableService` (payment method `crediario` = store credit installments, with `paid_installments` marking some as already received); purchases generate `AccountPayable` via `PayableService`. Canceling the sale/purchase must cancel its financial records, and a sale becomes `completed` once all receivables are `Received`/`Cancelled`.
When changing any of these flows, check the stock and financial effects together.

### Sales rules (do not regress)
These rules come from the November 2026 sales review. The customer-facing write-up (before / why / fix / now for each bug) is in `README.md` under "Correções em vendas".
- **Discount:** `sales.discount` is persisted; `total = subtotal − discount`, computed in one place in `SaleService` for create and update. A discount above the subtotal is a 422. Receivables, crediário entry, `installment_value`, the credit limit and the receipt all use the discounted total. Before the fix the column did not exist and the API dropped the field, so sales were saved at full price.
- **Installments:** split in cents with floor; the remainder goes on the last one (`220/3 = 73.33 + 73.33 + 73.34`). The API and the front (`utils/sale-installments.ts` → `splitInstallments`) must use the same rule. Each installment used to be rounded alone and lost cents.
- **Crediário entry is optional:** `crediario_entry` accepts 0 or nothing (`min:0`); it only has to be below the total. Without an entry the whole total is financed, no "Entrada" receivable and no "Entrada recebida" event are created, and the credit limit checks the whole total. It used to be required (`min:0.01` plus a check in `ensureCrediarioIsAllowed`, and `gt(0)` in the form).
- **Crediário:** the first due date comes from `first_installment_date` (default sale date + 30 days), then month by month clamped to month end. Installments split the financed balance (total − entry), not the total. The credit limit counts only open receivables and excludes the sale being edited. `paid_installments` is sent on update too, otherwise paid installments were recreated as open.
- **Stock:** every create/update/cancel/delete derives the delta from the sale's own `StockMovement` balance, never from the status. Stock leaves on creation in any status. Edit applies only the item diff. Cancel and delete return only what the sale still holds, so the stock comes back once, whatever the order of actions. The old code branched on status, which returned stock on completed → pending and did not adjust pending sales.
- **Cancel:** cancels open/partial receivables, keeps received ones, and returns stock in the same transaction with the sale locked. Settling or reversing a receivable of a cancelled sale is a 422. Before, cancel only flipped the status, and receivable settlements re-derived the sale status and "un-cancelled" it.
- **History:** `sale_events` via `SaleHistoryService` (registered, edited, payment received/reversed, delivered, completed, cancelled). It keeps `completed_at`/`cancelled_at` in sync with the status.
- **Front:** details read each installment's `total_amount` (`amount` is the open balance and is 0 once received/cancelled). Date-only timestamps (`T00:00:00Z`) are shown without timezone conversion (`formatReceivedAt`), otherwise Manaus shows the previous day. Legacy `payment_method` values `card`/`installment` keep labels and filter options. Money inputs are built with `Math.round(value * 100)` (`toMoneyInput`), because `19.99 * 100` is `1998.9999…` and the mask turned it into a huge price.
- **Receipt** (`utils/sale-documents.ts`): the digital preview and the A4 PDF are built from the same `buildReceiptData(sale)`, so they always show the same thing. Status is colored (Paga/Pendente/Cancelada), and the balance comes from the entry and the installments (it used to be derived only from the status, which printed "Valor pago R$ 0,00" on crediário with an entry). Crediário installments are listed with their due dates, and the PDF uses `jspdf-autotable` so long sales break pages. Unsaved sales (`id = 0`) print "Nova venda" (`formatSaleNumber`, also used by ESC/POS). Every user text that goes into the `srcDoc` HTML passes through `escapeHtml`. The digital mode also saves the receipt as an 80 mm PDF (`downloadSaleThermalPdf`: the thermal layout drawn with jsPDF, page height measured from the content) for sending to the customer; the dialog shows "Formato do PDF: A4 | 80 mm". Paid/remaining on the thermal HTML, the 80 mm PDF and ESC/POS come from `getSaleBalance` (entry counts as paid on a pending crediário). To check the PDF without a browser, load the module with Vite's `ssrLoadModule` (with `jspdf` external) and rasterize with `pdftoppm`.
- **Wizard** (`sales/components/create-edit-modal/`): 4 steps (products → client & cart → payment → summary). Steps 2 and 3 are one `StepCard` (centered, `max-w-3xl`, sections divided by borders), each part a `StepSection` (icon + title + description) ending in `TotalsSection`. Payment options come from `CHECKOUT_PAYMENT_OPTIONS` (label, hint, icon). Adding a product shows an inline confirmation (`CartAddedNotice`). The summary is a single card that asks "O cliente já pagou?" (`SALE_PAYMENT_ANSWERS`), or which installments were paid on crediário. The form is remounted on every open (`key` on `SaleForm`), otherwise it reopened with the previous sale. The modal closes only after the API saves, so a 422 keeps the cart.
- **Not recoverable:** discounts of sales saved before the fix were never stored. Pending sales cancelled before the fix never had their stock returned, and stock has moved since, so they were left as is.

### Purchases rules (do not regress)
These rules come from the November 2026 purchases migration (same pattern as sales). The customer-facing write-up is in `README.md` under "Compras".
- **Listing:** `GET /api/purchases` takes `IndexPurchaseRequest` (filters `supplier`, `product`, `category_id`, `brand_id`, `status`, `payment_method`; sort `date`, `due_date`, `total`, `created_at`; period on `date`). Without parameters it answers as before (15 per page, newest first), which Visão Geral and Relatórios rely on through `usePurchases()`. The resource returns `supplier_name`, `notes`, and `payables` on the show endpoint.
- **Stock:** create/update/cancel/delete use `StockMovementService::reconcile` with `reference_type = 'purchase'`. The target is the negative quantity per product (stock that came in), lines of the same product added up. Cancel and delete take out only what the purchase still added, so delete after cancel does not take it out twice. The old code took stock out once on cancel and again on delete, and the edit diff was keyed by product, so a second line of the same product overwrote the first.
- **Payables on edit:** `PurchaseService::syncPayables` rebuilds the payables only when what defines them changed (total, payment method, boleto term, date, due date or status). Notes, supplier, or items with the same total only refresh `supplier_id` and the item summary (`PayableService::syncPurchaseDetails`). A purchase that stays pending and already has a payment settled in contas a pagar cannot change those fields (422); the user must undo the settlement first. The old code always deleted and recreated the payables, which silently dropped payments.
- **Boleto:** `boleto_term_days` (30–150) means one boleto every 30 days: 60 = 2 boletos, at 30 and 60 days after the purchase date (`addDays(30 * n)`, not months). The leftover cents go on the **first** boletos (`PayableService::regenerateFromPurchase`). `purchase.due_date` is the last due date. The wizard preview (`splitBoletos`) mirrors this exactly. Non-boleto purchases store `boleto_term_days = null`.
- **Paid boletos:** create/update accept `paid_installments` (boleto numbers 1–5, only for boleto). `PurchaseService::syncPaidBoletos` settles the marked ones (`paid_at` = today, `paid_method = boleto`), sets unmarked paid ones back to pending (partial payments are left alone), and the purchase becomes completed only when no boleto is open. The summary step lists the boletos to mark instead of a single "Paga/Pendente" answer, so "Paga" no longer means every boleto was paid; the edit starts with the boletos already paid in contas a pagar (`getPaidBoletos`).
- **Cash:** a cash payable is always created as paid, so the wizard always sends `status = completed` for Dinheiro (a pending cash purchase used to stay pending forever with a paid payable).
- **Notes:** `purchases.notes` (≤ 1000 chars). The old dialog had the field but never sent it.
- **Front:** module in `pages/dashboard/purchases/` with the sales wizard copied, not shared (products → supplier & cart → payment → summary). No discount, no receipt/print. "Novo fornecedor" reuses the suppliers `CreateEditModal` (alias import) with the new `initialName` prop. Table columns: Data, Vencimento, Fornecedor, Produto, Categoria, Marca, Total, Status, Pagamento (method plus boleto count, "Boleto 3x"; the export keeps M. Pagamento and Boletos apart). Cancelled purchases are listed (the old screen hid them).
- **History:** `purchase_events` via `PurchaseHistoryService`, same shape as the sale history (registered, edited, payment made, completed, cancelled; reversals are `updated` events). Payables are rebuilt on some edits, so payments made or undone while saving are found by diffing `paidSnapshot()` (amount paid per installment number, taken before the change) with what is paid after (`recordPaymentChanges`), never by payable id. `PayableService` settle/partial/unsettle record the payment and call `syncStatus`, which keeps `completed_at`/`cancelled_at` in sync. Purchases saved before it got their history from the backfill migration (`2026_11_06_000600`, idempotent). The details page renders it with the shared `HistoryTimeline`.
- **Details → payables:** the "Contas a pagar" card (`DetailsCard` `action` prop) has "Ver em contas a pagar" (`/dashboard/accounts-payable?purchase={id}`) and each installment links to its payable. Sales mirror it: the card is "Contas a receber" (it was "Parcelas") and links to `?sale={id}`.

### Accounts receivable / payable rules
Both screens follow the same module pattern (`pages/dashboard/accounts-receivable`, `pages/dashboard/accounts-payable`, generated from the same shape; each create form takes the payment methods of its side: sales for receivables, purchases-like boletos for payables).
- **Listing:** `IndexAccountReceivableRequest` / `IndexAccountPayableRequest`. The filters are `customer` / `supplier` (by name) and `description` (on `item` or `description`). `origin` is `sale`|`manual` or `purchase`|`manual`. `status` also accepts `cancelled`. Sort keys: `amount`, `due_date`, `entry_date`, `created_at`. The period filter applies to `due_date`. Cancelled records stay hidden unless the status filter asks for them. Without parameters the API answers as before, which `useAccountReceivables()` / `useAccountPayables()` rely on (Visão Geral, Relatórios and the sales details and modal). The resources return `customer_name` / `supplier_name`. The `sale` / `purchase` filter (an id) shows only the accounts of one sale or purchase; the page shows `OriginFilterNotice` with "Ver todas" while it is set.
- **Columns:** Lançamento, Vencimento, Cliente/Fornecedor, Descrição, Parcela, Origem, Valor, Status. Origem is a link to the sale or purchase.
- **Selection:** the left checkbox column is the `selection` prop of the global `ServerTable` (no other screen uses it). Selected rows live in a `Map` in the page, so they survive pagination. The batch bar (`SelectionBar`) floats fixed at the bottom of the content area: `sticky` does not work because the layout `<main>` has `overflow:auto` and grows with the content. Actions: settle all, partial settle (exactly one open row), undo (only fully settled rows; the API cannot undo a partial).
- **Settling:** like the old screens, settle and partial settle record today in Manaus (`todayInAppTimeZone`). Payables are recorded as `paid_method = pix`. The old receivable partial settle used `new Date().toISOString()`, which recorded the next day after 20h.
- **Installment label:** sale or purchase installments read `n/total`, the crediário entry reads "Entrada", and a single or manual record reads "Única".
- **Manual records:** both take a status (pending or received/paid, the latter stores `amount_paid = amount` on the entry date) and a due date (≥ entry date).
  - **Receivable:** the payment methods of a sale (`cash`|`pix`|`card_debit`|`card_credit`|`crediario`), shown like the sale checkout (Dinheiro, PIX, Cartão with Débito/Crédito, Crediário). Crediário takes `installments` (1–24) and `due_date` is the first installment; `ReceivableService::createManual` splits it like a sale (floor in cents, leftover on the **last** one, month by month with `addMonthsNoOverflow`) and the installments always start open. The form preview (`splitCrediario`, on `splitInstallments`) mirrors it. `total_installments` and `payment_method` are stored on the row. Do not offer boleto here: it is a payable method. Manual receivables saved before this have no due date.
  - **Payable:** payment method `cash`|`pix`|`card`|`boleto`; boleto (`boleto_term_days` 30–150) is split month by month from the entry date (`PayableService::createManual`, `addMonthsNoOverflow`), with the leftover cents on the first boletos; the form preview (global `utils/manual-boletos.ts` → `splitManualBoletos`) mirrors it. This differs from purchases, which use 30-day steps. The edit form only shows the fields the update endpoint accepts. Validation: the receivable amount must be > 0 (it was `min:0`), and the payable notes have a 1000-character limit (there was none).
- **Overdue:** `status=overdue` (filter only, "Vencida") lists open (pending/partial) accounts due before today in Manaus, the same rule as the "vencidas" on Visão Geral. The "Pagamentos atrasados" alert counts payables that way and opens `/dashboard/accounts-payable?status=overdue`; "Compras a pagar" opens pending purchases (it counts purchases); "Produtos sem estoque" counts active products only, like the inventory list.
- **Summary cards:** "Total recebido/pago" adds `amount_paid`, so partial payments count. The old cards counted only fully settled rows.
- **Legacy data fixes** (production dump of 2026-11-06, run before the history backfills): `2026_11_05_231250` sets `amount_paid = amount` on received/paid accounts saved before `amount_paid` existed (12 receivables, R$ 12.911,04, were 0), and `2026_11_05_231260` completes pending sales whose receivables are all received/cancelled (3 sales). Both are idempotent; `tests/Feature/Finance/LegacyDataFixesTest.php`.
- **Details:** `/dashboard/accounts-receivable/{id}` and `/dashboard/accounts-payable/{id}` show the summary (with a link to the sale or purchase), the values and the notes, plus the payment method and payment notes on payables. Their actions are settle, partial, undo, edit and delete. Edit and delete stay available for linked records, as before.

### Period filter
`previous-month` ("Mês anterior", the whole previous calendar month) sits next to `current-month` in every period filter (`components/filters/period-filter.tsx`, `utils/period-range.ts` → `getMonthRange`, `use-server-table-state`, `use-table-query-state`). On Visão Geral it is compared with the month before it.

### Frontend
- React 19 + TypeScript + Inertia v3, React Compiler enabled, Tailwind v4, shadcn-style components in `components/ui`.
- Data flow: `lib/apiClient.ts` (fetch wrapper, `credentials: 'include'`) → `services/<entity>.ts` → TanStack Query hooks in `hooks/use-<entity>.ts` (export query keys; mutations invalidate related keys, e.g. sales invalidate products/customers/receivables) → module components. API entity TypeScript interfaces live in `schemas/`.
- Cache (`lib/query-provider.tsx`): `staleTime` 5 min and `gcTime` 30 min, so coming back to a page shows it at once; every mutation invalidates the lists it changes (receivable settlements also invalidate customers, whose open balance feeds the crediário limit). `ApiService.list()` without `page` loads every page with `per_page=100` (`TableIndexRequest::MAX_PER_PAGE`) and requests the pages after the first in parallel: Visão Geral went from 77 sequential requests to 16 on the production data.
- Visão Geral (`pages/dashboard/index.tsx`, panels in `components/overview/`): KPIs, charts and alerts show skeletons on the first load (`isLoading`) and an "Atualizando" hint while a cached view refreshes (`isRefreshing`). The chart skeleton is an overlay so the measured width survives the load. Trend percents use a comma and at most 2 decimals, without a thousands separator ("13.916%" was 13 916 % and looked like 13 with three decimals); "Mês atual" compares with the same days of the previous month, and every trend names the exact window it compares with (`formatComparisonRange`: "vs. 01/10 a 06/10"), a choice made with the user because "vs. mês passado" read as the whole month. The Contas a Receber/Pagar KPIs ignore the period (all open accounts) and say so with a "Todo o período" note (`scopeNote`, tooltip opening to the right so it does not cover the card).
- Tables (`components/table/server-table.tsx`): cells use `px-3`, filtered headers `min-w-24`, and the page gutter matches the header (`md:px-4`), so every module fits a 1440 px screen with the sidebar open, without horizontal scroll. Keep new columns compact. `NamesCell` (global) shows the first name in full (wrapping) plus a bold "+N" chip whose tooltip lists the others; with a `query` (the product filter) the matching name comes first, highlighted. `RecordLink` is the one look for links to another record (orange, `ArrowUpRight`): Origem in contas, the counts in categories/brands, the installments in sale/purchase details. `showView={false}` hides the eye (categories and brands, for now). **Filter notice:** when a table opens with filters in the URL (a link from another screen: alerts, categories/brands → inventory, sale/purchase → contas), `ServerTable` shows `FilterNotice` ("Mostrando só Status: Vencida" + "Ver tudo", which clears only those filters); it goes away once the user edits them. Labels come from the column filter options; filters without a column pass `filterLabels` (`sale: (id) => 'contas da Venda #id'`). Every new filtered link gets it for free, so link to tables with plain query params (`?status=pending`). Sales, purchases, clients, suppliers and products also accept `filter[id]` (one record, tenant-scoped); "Últimas atividades" on Visão Geral links there (`/dashboard/sales?id=230`, notice "Venda #230" / "Cliente: name"). Sales and purchases show one Pagamento column ("Crediário 3x"); clients show Crediário as the Ativo/Inativo chip (`StatusBadge` with `label`).
- Forms use `react-hook-form`; currency inputs use BRL masks; dates are formatted in the `America/Manaus` timezone.
- `resources/js/actions`, `resources/js/routes`, `resources/js/wayfinder` are **generated by Wayfinder** — don't edit by hand.

### Front-end module structure
Modules (inventory, clients, suppliers, categories, brands, sales, purchases, accounts receivable and payable) live entirely in `resources/js/pages/dashboard/<module>/`. Auth (`pages/auth/`: the Fortify page files plus `components/` and `utils/`) and the landing (`pages/home/`, Inertia component `home/index`) follow the same shape. Reports, settings and team keep their page files (`pages/dashboard/<module>.tsx`) with their components in `pages/dashboard/<module>/components/` until they are redone. Global pieces are in `components/` (`overview/`, `filters/period-filter.tsx`, `workspace-context.tsx`, `company-switcher-modal.tsx`, `table/`):
- `index.tsx` (list page, `ServerTable` + `useServerTableState`) and `show.tsx` (details page built with `components/details-page.tsx`).
- `components/<name>/index.tsx`: one component per file, named after its folder; never two components in one index and no re-exports. Big dialogs are split into sibling files inside the folder (e.g. `sales/components/create-edit-modal/`). The create/edit modal is always `CreateEditModal`.
- `utils/constants.ts` (every fixed object/label map), `utils/functions.ts` (functions and module-only hooks), `utils/schemas.ts` (Zod, mirroring the backend FormRequest rules, messages from `constants/validation-messages.ts`), `utils/types.ts` (all types, props included).
- Code used by 2+ modules is global (`components/`, `utils/`, `hooks/`). Exception: cadastro modals (product, client, supplier, category, brand) stay in their module and other modules import them with an alias (`import { CreateEditModal as ClientCreateEditModal } ...`).
- Forms: React Hook Form + shadcn `Form` + Zod. Keep comments minimal (no banners).

### Base path
Production is served under a `/operis` path prefix on the host domain, so Laravel itself sees `/api/...` (`config/api.php`) while the browser calls `/operis/api` (`resources/js/config/api.ts`). Vite `base` comes from `VITE_APP_BASE_PATH` (default `/operis`). Keep URLs relative to these settings rather than hardcoding `/` or `/operis`: build them with `withAppBasePath()` (`resources/js/constants/workspace.ts`), as `config/api.ts` does.

Local development: `.env` holds the dev settings (`APP_URL=http://localhost:8000`, empty `ASSET_URL` and `VITE_APP_BASE_PATH`, `SESSION_PATH=/`) and `.env.production` (gitignored) keeps the production values. Restart `composer run dev` after changing `VITE_*` variables.

### Public landing page & SEO
`/` renders the landing (`resources/js/pages/home/`, component `home/index`; `app.blade.php` keeps it light-only by that name) for guests and redirects signed-in users to the dashboard. SEO text, keywords, the FAQ and the "Últimas atualizações" entries (`updates`, the 3 newest are shown; write them for customers) live in `config/landing.php`; the FAQ is sent to the page as an Inertia prop and also printed as FAQPage JSON-LD by `resources/views/partials/landing-seo.blade.php`, so both always match. Meta/Open Graph tags are server-rendered (no SSR). `public/robots.txt`, `llms.txt`, `og-image.png` (source: `docs/brand/og-image.html`) and the favicons are copied to the web dir on deploy; crawlers only read robots.txt at the **domain root**.

### Keeping "Últimas atualizações" current
Whenever a change is significant for customers (a new feature, a noticeable improvement, or a fix they would notice), add an entry to `updates` in `config/landing.php` in the same change: `date` (YYYY-MM-DD of the change), `type` (`novidade` | `melhoria` | `correcao`), a short `title` and a one-sentence `description` written for the customer (no technical/commit language, no promises the code does not keep). Internal work (refactors, tests, deploy, tooling) does not go there. The landing shows the 3 newest automatically.

### Dev auth bypass
`BypassAuth` (web middleware) auto-logs in the first user when `BYPASS_AUTH=true` in `.env`. Middleware priority runs `Authenticate` before it on `auth` routes, so it only logs in on a public route: open `/` first. `php artisan serve` keeps the env it started with, so restart it after changing the flag.

## Deployment & commits
- Push to `main` deploys to production (cPanel, FTP only — no SSH) via `.github/workflows/deploy-production-ftp.yml`: CI builds a single `release.zip` (code + `vendor` + `public/build`), uploads it plus `.github/deploy/receiver.php` (as `_deploy.php` in the web dir), then POSTs to the receiver, which swaps app dirs, copies public assets (preserving the server's `index.php`/`.htaccess`) and runs `migrate --force`, `config:cache`, `event:cache`, `view:cache`, `queue:restart`. Routes are deliberately **not** cached (`route:cache`/`optimize`): served from the `/operis` subdirectory, Laravel's compiled route matcher returns 405 for the root URL `/operis/`. Be deliberate about what lands on `main`; new migrations run automatically on deploy.
- Server layout: app at `~/repositories/Operis-Saas`, web dir `~/public_html/dg/operis` (https://www.dgcomputer.com.br/operis). Previous release is kept in `storage/app/deploy/previous` for manual rollback.
- Commit messages follow `.agents/skills/commit-convention.md`: `type(area): summary` with types `feat|fix|docs|chore`, plus a bulleted body listing what changed.
